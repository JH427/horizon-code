# Horizon Code v0.1 design

Status: v0.1 tracer bullet implemented and validated against the exact local Qwen3.8-27B lane on 2026-08-25.

## Product brief

Horizon Code is a local-first coding harness written in Go for the exact Qwen3.8-27B model running on Horizon. It is not a general provider SDK and not a Go port of Pi.

- Repository: `https://github.com/JH427/horizon-code`
- Target model: Qwen3.8-27B
- Initial runtime: llama.cpp OpenAI-compatible server
- Default endpoint: `http://127.0.0.1:8080/v1`
- Default model alias: `qwen38-27b`
- Reference harness: Pi's agent architecture and interaction model
- UI: Bubble Tea, Lip Gloss, Bubbles, and Glamour

Current local inference lanes:

| Lane | Model | Context | Status |
| --- | --- | ---: | --- |
| rollback/control | Q4_K_M + BF16 mmproj | 262,144 | configured, currently stopped |
| quality/performance experiment | ROCmFP4 Strix + MTP | 65,536 | configured, currently stopped |

The first tracer bullet must fit the 65,536-token lane. Initial active-context budgeting therefore targets 48K tokens, leaving room for reasoning, tool traffic, and output. Larger contexts are experiments, not v0.1 requirements.

## Verified Qwen behavior to preserve

The official Qwen3.8-27B model card and chat template establish the following:

- Thinking is enabled by default.
- Supported reasoning efforts are `low`, `medium`, and `xhigh`; the template defaults to `xhigh`.
- Preserved thinking defaults to enabled.
- Recommended thinking-mode sampling is temperature 1.0, top-p 0.95, top-k 20, min-p 0.0, presence penalty 0.0, and repetition penalty 1.0.
- Native context is 262,144 tokens.
- The native tool dialogue is XML-like: `<tool_call><function=...><parameter=...>` with tool results represented inside `<tool_response>`.

Sources:

- https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/README.md
- https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/chat_template.jinja

These are upstream claims and protocol facts, not local performance results. Every runtime feature must be confirmed against the exact local llama.cpp build.

## Architecture

```text
cmd/horizon-code
      |
      v
internal/app -------- config, dependency wiring, lifecycle
      |
      +---- internal/agent ---- turn state, budgets, verification gates
      |            |
      |            +---- internal/model/qwen ---- SSE transport, Qwen options
      |            +---- internal/tools -------- validation and execution
      |            +---- internal/session ------ append-only event log
      |
      +---- internal/tui ------ event consumer and input producer
```

The agent core emits typed events. The TUI renders those events but does not control agent policy. This preserves a future headless mode without implementing an app server in v0.1.

## Protocol boundary

Horizon Code should preserve Qwen's native tool dialect without leaking XML throughout the codebase.

1. The harness sends OpenAI-compatible tool schemas to llama.cpp.
2. llama.cpp's Qwen chat template renders those schemas in Qwen's native XML dialect.
3. The client consumes normalized streaming text, reasoning, and tool-call deltas when the server provides them.
4. The model package normalizes a completed call into a typed `ToolCall`.
5. Tool results are sent through the OpenAI-compatible message API so the runtime renders native `<tool_response>` content.
6. Raw response fragments are optionally captured for protocol diagnostics.

Do not hand-author a second XML prompt in v0.1. Direct XML parsing is a compatibility fallback only if the exact llama.cpp server fails to normalize calls reliably.

## Core data model

```go
type TurnID string
type ItemID string

type Event struct {
    TurnID TurnID
    ItemID ItemID
    Kind   EventKind
    Time   time.Time
    Data   EventData
}
```

Each visible item follows a lifecycle:

```text
item.started -> zero or more item.delta -> item.completed
```

Initial item kinds:

- user message
- reasoning
- assistant message
- tool call
- tool result
- verification notice
- error

A turn begins with user input and ends only after a final answer, cancellation, budget exhaustion, or fatal error. The thread/session is an append-only sequence of turns. This borrows the useful item/turn/thread separation described by Codex without implementing JSON-RPC or a multi-client daemon yet.

Reference: https://openai.com/index/unlocking-the-codex-harness/

## Agent loop

The v0.1 loop is model-led with harness-enforced safety and completion gates:

```text
UNDERSTAND / LOCATE / INSPECT
             |
             v
          tool call ---- validate ---- execute ---- bounded result
             ^                                      |
             |______________________________________|
             |
             v
            EDIT ---- mark workspace dirty
             |
             v
          VERIFY ---- diff and targeted check required before success
             |
      pass --+-- fail
             |     |
             v     +---- REPAIR (bounded)
           FINAL
```

The phase labels are telemetry and prompt nudges, not a rigid workflow engine. The harness enforces only concrete invariants:

- malformed calls do not execute;
- read/write paths cannot escape the workspace;
- command execution is cancellable;
- tool outputs are bounded;
- a dirty workspace cannot be reported as successfully completed without verification evidence;
- all managed background jobs, including inspect-purpose jobs, must finish or stop before a verification command starts; completion during verification still requires a fresh check;
- conversation history persists between turns in the same engine, while execution budgets reset; interrupted tool exchanges are closed with explicit uncertain-result placeholders;
- turn, tool-call, repair, and token budgets terminate loops;
- journal failures cancel execution and reject later turns until restart; shutdown cancels and joins active work before resources close.

## v0.1 tool scope

The original tracer bullet exposed only `read_file`. The implementation now includes the following typed tools, covered by deterministic tests; the safe tools were also exercised in live Qwen3.8 turns:

1. `list_files` — bounded, sorted directory entries without reading file contents.
2. `read_file` — bounded numbered UTF-8 text.
3. `search_code` — bounded ripgrep regex results.
4. `edit_file` — atomic exact-match replacement; uniqueness required by default.
5. `create_file` — new files only; refuses overwrite.
6. `run_command` — no shell; allowlisted build, test, check, and read-only Git commands when Git is available.
7. `git_diff` — bounded staged or unstaged diff inspection, registered only when the workspace is inside a Git worktree.
8. `apply_patch` — transactional exact replacements across multiple existing text files with rollback on promotion failure.
9. `make_directory` — creates a workspace directory hierarchy.
10. `move_path` — moves or renames a workspace entry without overwriting.
11. `delete_path` — deletes a workspace entry; recursive directory deletion must be explicit.
12. `exec_command` — broad structured argv execution in workspace/operator modes; direct shell programs require operator authorization.
13. `background_process` — starts, polls, lists, and stops bounded process groups; all remaining jobs are stopped when Horizon Code exits.
14. `shell` — operator-only `bash -lc` execution with bounded output, timeout, and process-group cancellation.

Typed filesystem paths and command working directories are workspace-relative and symlink escapes are rejected. Broad executables are not an operating-system sandbox; operator shell is intentionally unrestricted. All arbitrary foreground, shell, and background execution conservatively marks the turn dirty, including commands used for inspection and failures after process start. Shell and background jobs cannot self-attest verification; only the hardened `run_command` lane or an `exec_command` accepted by the same build/test/static-check validator can clear pending verification.

Do not add planner, reviewer, AST index, embeddings, MCP, plugins, multimodal input, or multi-agent orchestration before the live tracer bullet and baseline eval.

## Qwen defaults and experiments

Initial defaults:

```text
enable_thinking = true
preserve_thinking = true
reasoning_effort = medium
temperature = 1.0
top_p = 0.95
top_k = 20
```

`medium` is a product default, not an upstream recommendation; upstream defaults to `xhigh`. Use `xhigh` for complex debugging and review experiments. Do not assume `low` is faster end to end: the model card explicitly warns that weaker per-turn reasoning can increase retries and total latency.

The local runtime now round-trips Qwen reasoning content correctly. Horizon Code deliberately exposes streamed model reasoning in the transcript and session log for operator visibility, alongside a compact activity state. Users should treat session logs as private because reasoning and tool results can contain workspace content.

## Context strategy

Keep a cache-friendly stable prefix:

1. system instructions;
2. tool schemas;
3. hierarchical repository policies (`HORIZON.md`), discovered from filesystem root through the selected workspace, source-labeled broadest-to-most-specific, and rejected when their combined content exceeds 64 KiB;
4. compact repository map;
5. user task.

Dynamic tool calls and results follow. Do not dump the repository into context. v0.1 does not need embeddings. Start with paths, file sizes, language hints, and later symbol extraction only if measured retrieval failures justify it.

The initial tracer bullet excluded compaction; the current implementation deterministically compacts older complete tool rounds. Retained conversation history is subject to the same active-context ceiling as the current turn. It preserves user requests and recent evidence, failing closed if compaction cannot bring the request within budget. JSONL replay is evidence inspection, not automatic model-context restoration.

## TUI acceptance criteria

The initial screen contains:

- scrollable transcript;
- multiline composer;
- a single compact flight-deck rail with activity, exact/estimated context, cumulative server-reported tok/s, output tokens, and model step;
- both the enforced 48K active-agent budget and verified 262,144-token served window, labeled as different limits;
- visible tool-call cards with pending/running/succeeded/failed states;
- cancellation key that propagates to the HTTP request and tool context;
- usable layouts at 80x24 and wide terminals;
- centralized theme tokens and no animation that delays interaction.

The terminal presentation is intentionally borderless: no boxed transcript, oversized brand banner, startup filler, or permanent help panel. `HORIZON.md` files are discovered broadest-to-most-specific and injected into the system message under a strict 64 KiB aggregate budget. Capability authorization is injected as a separate authoritative system section and is enforced by tool registration; workspace instructions cannot override it.

Capability exposure is explicit. `safe` retains confined typed tools and verification-only commands; `workspace` adds patch/path operations, broad structured command execution, and managed processes; `operator` adds a dedicated unrestricted shell. Command working directories remain workspace-relative, but `workspace` is an ergonomic structured-exec mode—not a security boundary: executables, interpreters, and wrappers retain the current user's operating-system permissions. The selected mode is visible in the Flight Deck.

Before failing the active 48K context budget, the agent deterministically compacts older complete assistant/tool rounds into a bounded source-labeled summary. It preserves the original user request, recent complete rounds, current verification state, and tool-call/result protocol integrity. Raw session evidence remains unchanged.

Colors use semantic ANSI terminal palette slots and never paint a custom application background. Omarchy theme changes therefore flow through the terminal palette instead of requiring a parallel Horizon Code theme registry.

llama.cpp requests set `timings_per_token: true` and `stream_options.include_usage: true`. Live timing chunks provide exact cumulative `predicted_per_second` and timing-derived context; terminal OpenAI usage is authoritative for final prompt/completion/total tokens. The pre-request bytes/3 guard remains a conservative client estimate and is rendered with `~`, never as exact tokenization.

The TUI receives events through a channel and maps them into Bubble Tea messages. No model or tool package imports Bubble Tea.

## Testing and measurement

Three levels:

1. Unit tests: SSE parsing, tool-call assembly, schema validation, path confinement, truncation, budgets, event reduction.
2. Deterministic integration tests: fake model streams text, one tool call, malformed tool call, retry, final answer, and cancellation.
3. Real-model smoke: explicit command, exact Qwen3.8 model identity, read-only marker file, one tool call, strict timeout/token budget, captured runtime metadata.

Start with 8-12 representative pilot tasks, not a 50-task suite. First measure:

- valid tool-call rate;
- correct tool selection;
- final-answer success;
- time to first token and total wall time;
- prompt/reasoning/output token counts when available;
- tool calls and retries;
- premature completion;
- cancellation correctness.

Expand the corpus only after the runner and scoring are stable.

## 2026-10-02 lifecycle hardening

- The engine now retains conversation requests, accepted answers, and completed tool evidence across turns, rejects overlapping runs, and repairs incomplete assistant/tool exchanges with explicit unknown-result placeholders. Per-turn execution budgets remain independent from retained context.
- Verification is withheld when any managed job is running before or after the command, even if its purpose is `inspect`. A job that exits during a command cannot retroactively certify that command. Wait/stop first, then run a fresh check.
- The TUI derives turn contexts from the application's signal context. Renderer/input exit also cancels that context. The recording runner's shutdown barrier cancels and joins active work before the session store, tool resources, and owned server close.
- Session event-write failures propagate with their cause, cancel the runner, suppress unrecorded events, and prevent further turns until restart. Completion-write errors are retained even when execution also failed.
- Offline regressions cover conversation continuity, interrupted multi-call recovery, cross-turn compaction and budgets, background verification ordering, cancellation propagation, shutdown joining, and injected journal failures. Ordinary tests use fixtures/fake models and do not start inference; this change does not constitute a fresh Qwen live validation.

## v0.1 tracer-bullet completion

The milestone is complete only when all of these are executed and verified:

- endpoint health and exact model ID captured;
- streamed reasoning/text handled without corrupting the transcript;
- Qwen requests `read_file`;
- the harness validates and executes it with bounded output;
- the result returns to Qwen through the native template path;
- Qwen produces a final answer containing a marker known only from the file;
- cancellation leaves no running request or subprocess;
- deterministic fake-model tests pass;
- the opt-in real-model smoke passes on the exact local Qwen3.8-27B lane.
